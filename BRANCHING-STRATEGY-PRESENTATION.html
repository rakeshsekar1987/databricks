Advance Release Strategy

Working on Release 3.0 while 2.5 is in progress

develop (2.5)
advance/3.0
3.0 Feature A
3.0 Feature B
3.0 Feature C
Merge to develop
release/2.5.0
v2.5.0
🔮

When to Use Advance Branch

  • Feature won't make current release
  • Breaking changes that need isolation
  • Long-running feature development
  • Experimental features
🔄

Workflow

  • Create advance/3.0 from develop
  • Create features as feature/ADV-3.0-xxx
  • Merge to advance branch
  • After 2.5 ships, merge to develop
✨

Benefits

  • No blocking between releases
  • Parallel development streams
  • Clean separation of concerns
  • Easy to defer if needed

Version Bump Rules

PATCH (x.y.Z)

Bug fixes, security patches

2.3.0 → 2.3.1

Backward compatible

MINOR (x.Y.0)

New features, enhancements

2.3.0 → 2.4.0

Backward compatible

MAJOR (X.0.0)

Breaking changes, API changes

2.3.0 → 3.0.0

May break consumers

Summary: Key Takeaways

Enterprise Branching & Release Strategy

🌿 Branching Strategy

  • develop: Integration for current release
  • advance/*: Future release work
  • release/*: Stabilization
  • master: Production-ready
  • hotfix/*: Emergency fixes

🚀 Environment Flow

  • DEV: Auto-deploy on develop merge
  • QA: Auto-deploy on release creation
  • UAT: Manual gate with sign-off
  • Pre-Prod: Performance validation
  • Prod: Canary deployment

📦 JFrog Artifacts

  • Build Once: Same artifact through all envs
  • Promote: dev → rc → release
  • Immutable: Production artifacts locked
  • Scan: Security at each stage

🔧 Key Principles

  • #1: Isolated pipelines per service
  • #2: Independent versioning (SemVer)
  • #3: Progressive delivery (Canary)
  • #4: RBAC & GitOps governance
  • #5: Standardized templates
