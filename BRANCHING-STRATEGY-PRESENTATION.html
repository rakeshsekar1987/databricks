Advance Release Strategy

Working on Release 3.0 while 2.5 and 2.6 are in progress

🔶 When to Use Advance Branch

  • Feature won't make the current release deadline
  • Breaking changes that need isolation
  • Long-running feature development (2+ sprints)
  • Experimental features requiring validation
  • Major refactoring or architecture changes

✅ Advance Branch Workflow

  • Create: advance/3.0 from develop
  • Feature: feature/ADV-3.0-xxx from advance
  • Merge: Features merge to advance branch
  • Sync: Regularly rebase/merge from develop
  • Complete: Merge advance to develop when ready

Summary: Complete Strategy

Key Takeaways for Enterprise Microservice Deployment

🌿 Branching Strategy

  • develop: Current release integration
  • advance/*: Future release work (parallel)
  • release/*: Release candidate stabilization
  • master: Production-ready code
  • feature/*: Short-lived development (1-3 days)
  • hotfix/*: Emergency production fixes

🚀 Environment Flow

  • DEV: Auto-deploy on develop merge
  • QA: Auto-deploy on release creation
  • UAT: Manual gate with PO sign-off
  • Pre-Prod: Performance validation
  • Prod: Canary → Blue-Green deploy

📦 JFrog & Artifacts

  • Build Once: Same artifact through all envs
  • Promote: docker-dev → docker-rc → docker-release
  • Immutable: Production artifacts locked
  • Scan: Xray security at each stage

🔧 Key Principles

  • #1: Isolated pipelines per service
  • #2: Independent versioning (SemVer)
  • #3: Progressive delivery (Canary/Feature Flags)
  • #4: RBAC & GitOps governance
  • #5: Standardized templates
