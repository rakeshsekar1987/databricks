Purpose and deployment mapping for each branch

Branch Purpose Deploys To Merge From Merge To Approval

dev Development integration, feature merges DEV Environment master (cut-off), feature/* qa Code review
qa QA regression testing QA Environment dev uat QA Team

pre-prod Release validation gate (final review) ⚠️ NO DEPLOYMENT uat prod Release Manager
prod Production deployment PROD Environment pre-prod master Ops Team
Key Points

🔷 pre-prod Purpose

  • Final code review before prod
  • Release notes validation
  • Change request documentation
  • NO environment deployment
  • Gate for production approval

✅ master Purpose

  • Stores all successful releases
  • Version tags (v2.4.0, v2.5.0)
  • Source for next dev cycle
  • Cut-off point for new sprints
  • Rollback reference

🟢 prod → master Flow

  • After successful prod deploy
  • Validate in production (bake time)
  • Merge prod to master
  • Create version tag
  • Start next dev cycle from master

Bug Fix Strategy

Handling bugs at each stage: QA, UAT, and Production

🐛 QA Bug Fix

  • Branch from: qa
  • Naming: bugfix/QA-xxxx
  • Merge to: qa
  • No sync needed (not in uat yet)

🐛 UAT Bug Fix

  • Branch from: uat
  • Naming: bugfix/UAT-xxxx
  • Merge to: uat
  • Cherry-pick to: qa, dev

🔥 Production Hotfix

  • Branch from: prod
  • Naming: hotfix/PROD-xxxx
  • Merge to: prod
  • Cherry-pick to: ALL branches

Bug Fix Synchronization

Keeping all branches in sync after bug fixes

# Hotfix cherry-pick commands

git checkout prod
git checkout -b hotfix/PROD-9999
# ... fix the bug ...
git commit -m "fix: critical production bug PROD-9999"
git checkout prod && git merge hotfix/PROD-9999

# Cherry-pick to all other branches
git checkout pre-prod && git cherry-pick <commit-hash>
git checkout uat && git cherry-pick <commit-hash>
git checkout qa && git cherry-pick <commit-hash>
git checkout dev && git cherry-pick <commit-hash>

# After prod bake time, merge to master
git checkout master && git merge prod
git tag v2.5.1

Advance Release Strategy

Working on Release 3.0 while 2.5 is in progress

🔶 When to Use Advance Branch

  • Feature won't make current release
  • Breaking changes requiring isolation
  • Long-running development (2+ sprints)
  • Experimental or risky features

✅ Advance Branch Workflow

  • Create advance/3.0 from dev
  • Features branch as feature/ADV-3.0-xxx
  • Merge features to advance branch
  • After 2.5 releases, merge advance to dev

Summary

Complete Branching & Release Strategy

🌿 Branch Flow

  • master → Stable releases, cut-off source
  • dev → Development integration (DEV env)
  • qa → QA testing (QA env)
  • uat → User acceptance (UAT env)
  • pre-prod → Validation gate (NO deploy)
  • prod → Production (PROD env)

🐛 Bug Fix Strategy

  • QA bugs → bugfix/QA-xxx → qa
  • UAT bugs → bugfix/UAT-xxx → uat + cherry-pick
  • Prod hotfix → hotfix/PROD-xxx → prod + ALL branches
  • Always sync fixes to lower branches

🔄 Release Cycle

  • 1. Cut-off from master to dev
  • 2. Develop features on dev
  • 3. Promote: dev → qa → uat → pre-prod → prod
  • 4. After prod success, merge to master
  • 5. Tag version, start next cycle

📦 Key Principles

  • pre-prod = Validation only, no deployment
  • master = Source of truth after release
  • Build once, promote artifacts
  • Cherry-pick hotfixes to all branches
  • Advance branch for future releases
